0.2 Conventions & How to Read This Document ▼

This SRS follows a fixed contract so that humans and AI agents can parse it deterministically. Part I gives context that makes requirements unambiguous; Part II contains the requirements themselves; appendices carry traceability and supporting material.

IDs are permanent: they are never renumbered or reused. A withdrawn requirement keeps its ID with Status: Withdrawn.

Requirement statement grammar — EARS

Every requirement statement uses one of the EARS (Easy Approach to Requirements Syntax) patterns. The pattern keyword tells you what kind of behavior is specified:

PatternTemplateUse for
UbiquitousThe {system} shall {response}.Always-true properties
Event-drivenWhen {trigger}, the {system} shall {response}.Responses to events
State-drivenWhile {state}, the {system} shall {response}.Behavior during a state
Unwanted behaviorIf {condition}, then the {system} shall {response}.Error/failure handling
Optional featureWhere {feature is included}, the {system} shall {response}.Configurable/optional capability

One requirement = one shall. Compound behaviors are split into separate requirements. Vague verbs (support, handle, manage, be user-friendly) are forbidden in the shall-clause.

Acceptance criteria — Gherkin

Every requirement with Verification: TEST or E2E carries at least two Gherkin scenarios: one happy path and one failure/edge path. Scenarios are the executable test specification — the coding agent generates automated tests from them 1:1. Scenario steps reference concrete values, not adjectives.

Status rules

  • All four methods reach Verified autonomously — artifact + pass condition are the whole decision.
  • Human gates live elsewhere by design: INFERRED requirements need human approval before implementation (§0.2), and release-level acceptance (UAT) is a project gate, not a per-requirement verification method.
  • Every Must requirement is Verified before release; every Should is Verified or explicitly deferred with a recorded decision.

B SRS Quality Checklist ▼

  1. No invented scope (run this first): every requirement cites a source clause that actually says it — spot-check by quoting the clause. Every INFERRED requirement names the sourced requirement(s) it enables, passes the deletion test ("deleting it would leave a sourced requirement unimplementable or untestable"), and sits at Status Review until a human approves it. If more than ~1 in 10 requirements is INFERRED, the conversion has drifted into invention — stop and escalate.
  2. Coverage: every requirement-bearing clause of every source document is cited by ≥ 1 Source field or has a row in §2 Out of Scope; citations are clause-granular so the source → requirement index can be generated mechanically.
  3. Placeholders: no {curly} placeholder text remains anywhere.
  4. Examples: no data-status="Example" cards remain.
  5. Feature mapping: §5 features ↔ §7 groups are exactly 1:1.
  6. Testability: every card with Verification TEST or E2E has ≥ 2 Gherkin scenarios (happy + failure) using concrete values.
  7. Integrations: §4.1 rows ↔ §8 IC cards are 1:1; every IC states failure semantics.
  8. Mockups: every MCK-nn figure has a disposition (Binding / Illustrative), exhaustive alt text, and ≥ 1 ID in its Derives list — or a §2 row explaining why not; every interactive element visible in a Binding mockup traces to an FR/UX/ENT item.
  9. Data: every entity referenced by any FR/IC exists in §9.2 and appears in the ER diagram.
  10. Standards: every standard or regulation the source documents declare binding is cited — by name + clause — in the Source field of ≥ 1 requirement.
  11. Users: every §3 user class drives ≥ 1 requirement ID.
  12. Language: no shall-clause contains support, handle, manage, process appropriately, user-friendly, fast, robust, seamless, etc.
  13. NFRs: every NFR states a number or falsifiable condition plus its measurement context.
  14. Completeness: every template section is filled or explicitly “Not applicable — reason”.
  15. Machine-consistency: every card’s data-* attributes match its visible badges.
  16. Scaffolding: AUTHORING comments removed from the final instance; §0.2 retained.
